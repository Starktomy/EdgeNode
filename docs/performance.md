# EdgeNode 性能优化与调优顺序

本轮优先处理资源预算错误、请求路径的重复分配，以及故障重试时的内存峰值。以下收益来自本地微基准；生产 CPU、RSS 与吞吐需要相同流量和配置的前后对照测试。

## 已实现的优化

| 路径 | 改动与测量结果 |
| --- | --- |
| 资源预算 | 内存识别 cgroup v1/v2 及可见祖先限额；真实 256/512 MiB 容器的字节读取验证通过。`MaxCPU=0` 恢复 Go 容器调度默认值，显式环境配置优先。 |
| 内容缓存 | 去掉每存储至少 1 GiB 的下限，将有效内存的三分之一分摊给实际启用的内存存储，包括磁盘策略的内存层；纯磁盘策略不占该份额。 |
| 缓存元数据 | Origin+语言写入约 12.4 → 7.3 µs，73 → 41 次分配；压缩新增 Vary 字段时也能复用编码并正确失效。 |
| 回源连接池 | 满 4096 客户端并持续切换 Host 时，注册表操作约 48.2 → 1.63 µs；限定淘汰采样工作量，锁外关闭空闲连接。 |
| 流量统计 | 固定域名累计约 306 → 133 ns/op，104 → 16 B/op，8 → 2 次分配；计费总量和持久化身份语义保留。 |
| 日志与统计发送 | 按批读取。首批发送失败的 8 批积压基准，编码数据读取分配约降低 87.5%；全目录扫描仍为 O(N)。 |
| 文件句柄缓存 | 拒收文件时及时关闭；关闭与归还流程同步，防止描述符滞留和计数竞争。文件逻辑尺寸预算不等同于 RSS。 |
| 压缩器复用 | 修复对象交接竞争与请求引用滞留；deflate 解码约 18.2 → 7.6 µs，约 40.6 KB/次分配降到零。 |

方法、原始数据与取舍见 [内存/CPU](performance-memory.md)、[缓存元数据](performance-cache-origin.md)、[回源池](performance-origin-pool.md)、[投递](performance-delivery.md)、[压缩器](performance-compression.md)。

同时给恢复批次增加解码前的记录、重复元素和嵌套深度预算，防止很小的 protobuf 数据放大为大量内存对象。新日志按同一预算分批，超限旧文件保留原 ID 隔离；计数带来额外 CPU 开销，具体成本与兼容边界见投递文档。

## 优先调整哪些配置

1. **先约束工作集，再调整 GC。** 确认容器 memory/CPU quota；根据内存内容缓存、WAF 正文、压缩、队列及索引的实际占用设置容量。`GOMEMLIMIT` 是软目标，过低会增加 GC CPU，不能代替缩小工作集。
2. **按热点分配缓存。** 用 `maxCacheMemoryCapacity`、各缓存策略 `capacity` / `maxSize` 控制内容层；磁盘缓存的内存层也参与预算。旧配置将节点容量用作每存储上限的语义保留，不能把该字段当作整个进程的硬内存上限。
3. **减少不必要的实时转码。** 按 `compression` 的类型、`minLength` / `maxLength` 和条件匹配可压缩文本；已压缩图片、视频和归档避免重复压缩。热点内容可评估 `syncCompressionCache`，同时测量写放大与磁盘空间。WebP 转换限制对象尺寸与适用业务。
4. **明确正文和并发边界。** 设置 `requestLimit.maxBodySize`、`maxConns` / `maxConnsPerIP` 与 WAF 的 `maxRequestBodySize`，保留业务需要的检查。并发数乘以每请求正文、缓冲和压缩状态，是重要的峰值来源；限流行为也需验证。
5. **按复用率配置回源。** `origin.idleConns` 控制空闲连接，`maxConns` 控制活动连接；逐步调整，观察连接等待、握手、错误率和尾延迟。较少的空闲连接可能增加突发建连成本。

## 下一步适合重构的部分

- TTL/WAF/统计及索引缓存仍有按 GiB、条目数估算容量的路径；应引入统一的字节预算与可观测的淘汰计数，并验证高基数流量。
- spool 每次落盘和选取批次仍扫描目录；只有积压场景的 profile 证明其为瓶颈后，再引入可校验、能恢复和处理外部文件变化的索引。
- 压缩器池的容量和自动级别仍有宿主机启发式。应基于 CPU quota、算法状态实际尺寸及压缩比，单独验证缓存容量与并发成本。
- 热点锁与大量小对象分配先用 CPU、allocs、mutex/block profile 定位，再决定分片、批处理或缓冲复用；扩大全局对象池可能增加常驻内存和请求引用滞留。

测试机采样命令及隔离要求见 [内存文档](performance-memory.md)。至少分别覆盖静态命中、冷缓存回源、大对象流式传输、WAF 正文、压缩和 API 中断重试，记录 QPS、P95/P99、RSS、GC CPU、cgroup 节流、命中率、回源带宽及错误率。TLS 校验、租户隔离、WAF 检查和落盘持久性必须与性能一起验证。

## 本轮验证范围

使用 Go 1.27.4，`EDGE_VERIFY_JOBS=2 ./build/verify.sh all` 已通过模块校验、全包测试编译与 vet、命令构建、选定的实际 race 回归及 `govulncheck`。测试编译使用 `-exec /bin/true`，没有执行依赖生产配置或外部服务的全部旧集成测试；日志预算的完整 `TestAccessLog` 集合另行实际执行并通过 race。ARM64 使用 `CGO_ENABLED=1 CC=aarch64-linux-gnu-gcc GOOS=linux GOARCH=arm64 go build -tags=community ./cmd/edge-node` 交叉构建成功，未在 ARM64 硬件上运行。

上述压测、容器额度与 fuzz 证据均在独立测试环境完成，没有部署或重启生产节点。整体业务吞吐、RSS 和 CPU 改善仍待等效流量对照验证。
